Краткий обзор lsFusion

Краткий обзор элементов lsFusion для ИИ-агентов​

Формат: очень сжато, для понимания и генерации кода. Подробное описание и синтаксис извлекаются инструментами через RAG в документации.

Какая ветка: language — синтаксис инструкций и операторов; paradigm — концепции и библиотеки системных модулей; how-to — рецепты задач; brief — карта области, запрашивается через lsfusion_retrieve_docs(type='brief', query='<area>'); у большинства названных здесь областей она есть, а если поиск ничего не вернул — значит по ней есть только эта статья; rules — ограничения на код одной области. Если не уверены — не указывайте фильтр: по умолчанию поиск идёт по всем пяти веткам и объединяет их; исключены только две верхние статьи (эта и Rules), потому что lsfusion_get_guidance отдаёт их целиком.

Доменная логика — базовые элементы (от простых к сложным)​

Классы (Classes)​

  • Описание: базовый элемент — множество объектов. Задают типы объектов; используются в сигнатурах свойств и действий и как классы объектов формы. Наследование (может быть множественным). Встроенные и пользовательские классы. Полиморфизм через наследование, ABSTRACT + += / ACTION+, MULTI.
  • Аналогия: классы ООП, с множественной диспетчеризацией по классам параметров.
  • Инструкция (CLASS): CLASS ABSTRACT name [caption] [imageSetting] [: parent1, ..., parentN]; и CLASS [NATIVE] name [caption] [imageSetting] [{ objectName1 [objectCaption1] [imageSetting], ... }] [: parent1, ..., parentN]; для класса со статическими объектами

Свойства (Properties)​

  • Описание: вычисляют факты, не меняют состояние. DATA (хранятся в базе, если не объявлены LOCAL — те живут в сессии) и вычисляемые (формулы, агрегации, композиции).
  • Аналогия: математические / чистые функции. Декларативны, близки к SQL.
  • Инструкция (=): name [caption] [(param1, ..., paramN)] = expression [options];; хранимое — = DATA [LOCAL [NESTED [MANAGESESSION | NOMANAGESESSION]]] returnClass [(argumentClass1, ..., argumentClassN)] (DATA).

Действия (Actions)​

  • Описание: меняют состояние (БД или внешнее). Двойственны свойствам: свойства = что; действия = как это изменяется.
  • Аналогия: процедуры / методы. Императивны, близки к Java.
  • Инструкция (ACTION): name [caption] [(param1, ..., paramN)] { actionBody } [options]
  • Сессии изменений: изменения не попадают в базу по мере внесения — они копятся в текущей сессии, пока APPLY их не запишет, а CANCEL не отбросит; NEWSESSION и NESTEDSESSION выполняют действие в отдельной сессии. Во вложенной сессии APPLY копирует изменения в родительскую, а не пишет их, а внутри транзакции применения сессия не создается вовсе — действие откладывается в текущую.

События (Events)​

  • Описание: зависящие от времени реакции — глобальное событие выполняет действие в некоторый момент жизни сессии, чаще всего при изменении данных; событие формы — в точке жизни формы (INIT, APPLY, CANCEL, CLOSE, DROP), на действие пользователя, от клавиши до вкладки или выбора строки, либо по таймеру через ON SCHEDULE. Основная инструкция WHEN; <- WHEN объявляет вычисляемое событие: значение выводится при чтении свойства, а явная запись имеет приоритет; анализаторы изменений сессии CHANGED, SET, DROPPED, PREV и т. д. События формы навешиваются через ON: ON CHANGE/ON EDIT/ON CONTEXTMENU/ON GROUPCHANGE/ON CHANGEWYS. Инструкции BEFORE / AFTER задают действие-аспект, вызываемое перед / после другого действия.
  • Аналогия: триггеры БД, но шире.
  • Инструкции (WHEN, ON): WHEN eventClause eventExpr [ORDER [DESC] orderExpr1, ..., orderExprN] DO eventAction; и ON eventClause eventAction;

Ограничения (Constraints)​

  • Описание: не зависящие от времени инварианты над базой. Проверяются на событии, заданном eventClause; если оно не указано — на APPLY. Виды: общие (CONSTRAINT), простые — следствие =>, у которого есть клауза RESOLVE [LEFT] [RIGHT], указывающая платформе, какую сторону исправлять автоматически, и определенность NONULL [DELETE], у которой такой клаузы нет; уникальность агрегируемых объектов добавляют GROUP AGGR / AGGR.
  • Аналогия: CHECK и NOT NULL в SQL, но условием служит произвольное свойство над всей базой.
  • Инструкция (CONSTRAINT): CONSTRAINT [eventClause] constraintExpr [CHECKED [BY propertyId1, ..., propertyIdN]] MESSAGE messageExpr [PROPERTIES outExpr1, ..., outExprM];

Агрегации (Aggregations)​

  • Описание: агрегируемые объекты, которые платформа создаёт и удаляет по правилу — AGGR создаёт объект, когда агрегируемое выражение становится не NULL, и удаляет, когда оно снова становится NULL; срабатывает на изменениях, а не на уже существующих данных. GROUP AGGR возвращает объект группы. См. Brief: свойства и Brief: ограничения.
  • Оператор (AGGR): AGGR [eventClause] aggrClass WHERE aggrExpr [NEW [newEventClause]] [DELETE [deleteEventClause]]

Логика представления — та же модель, показанная пользователю или другой системе​

Формы (Forms)​

  • Описание: универсальный элемент данных/UI. OBJECTS (группы), PROPERTIES (что показывать / действия), FILTERS (фильтр строк). Представления: интерактивное (SHOW), печатное (PRINT), структурное (EXPORT/IMPORT). Расширяется через EXTEND FORM.
  • Аналогия: SQL-запрос, но шире (много таблиц сразу).
  • Инструкция (FORM): FORM name [caption] formOptions formBlock1 ... formBlockN;
  • Дизайн (DESIGN): интерактивное представление собирается из компонентов, которые платформа порождает по структуре формы; DESIGN их перемещает, скрывает и настраивает.

Навигатор и окна​

  • Навигатор (NAVIGATOR): меню / маршрутизация, связывающая формы и действия.
  • Окна (WINDOW): участки экрана, каждый из которых показывает свои элементы навигатора.

Физическая модель — из чего собран проект и как он исполняется​

Три части: разработка — модули, из которых собран проект, и всё, что касается их написания; исполнение — как подсказать платформе, где хранить и как обрабатывать данные, чтобы это работало быстро; управление — эксплуатация результата.

Модули (Modules)​

  • Описание: единица переиспользования (один .lsf-файл); содержит классы/свойства/действия/формы/события/ограничения; зависимости через REQUIRE.
  • Аналогия: пакет / сборка.
  • Инструкция (заголовок модуля): MODULE name; [REQUIRE moduleName1, ..., moduleNameN;] [PRIORITY namespaceName1, ..., namespaceNameM;] [NAMESPACE namespaceName;]

Системные модули (стандартная библиотека)​

Двенадцать из них платформа загружает сама, среди них System, Utils, Time, Authentication, — но загрузить не значит зависеть: объявления модуля становятся доступны через REQUIRE, и неявен только System. Какие это двенадцать и для чего нужен каждый — в Brief: модули.

Разработка и интеграция​

  • Идентификация, именование, миграция: элемент называется <пространство имен>.<имя>, а свойство и действие — этим плюс сигнатурой классов параметров; переименование или перенос в другое пространство имён меняет это имя, а перенос в другой модуль с тем же NAMESPACE — нет; migration.script переносит то, что сохраняет конкретный вид записи: PROPERTY сохраняет настройки, данные свойства требуют STORED PROPERTY.
  • Расширения: уже объявленные класс, свойство, действие или форма расширяются без правки самого объявления — обычно из другого модуля, так проект и собирается из модулей, но и внутри одного модуля тоже, где этим задают порядок инициализации.
  • Метапрограммирование (META, @): параметризованный метакод порождает повторяющиеся объявления вместо их копирования.
  • Интеграция: четыре направления — внешняя система обращается по HTTP; внутренняя — через Java API или напрямую к таблицам SQL; наружу к внешней системе зовет EXTERNAL; к внутренней — INTERNAL и FORMULA, в той же JVM или базе.
  • Интернационализация: подпись остается обычным текстом, пока в ней нет фрагмента {id}, — а он разрешается по ResourceBundle текущей локали; обратный перевод умеет подставить этот идентификатор за автора. Пользовательские данные не переводятся.

Исполнение — как подсказать платформе, где хранить и как обрабатывать​

  • Материализации (MATERIALIZED): вычисляемое свойство можно хранить в поле таблицы, а не считать при чтении; платформа поддерживает его в актуальном состоянии при изменении данных, от которых оно зависит, и пересчитывает по требованию, когда изменилось само определение.
  • Таблицы (TABLE): где живут хранимые значения — нелокальных свойств DATA и материализованных вычисляемых; объявляются классами своих ключей, и такое свойство без явно заданной таблицы размещается автоматически.
  • Индексы (INDEX): индексы по материализованным свойствам и ключевым полям таблицы; индексы по собственным ключам таблицы создаются автоматически.

Управление — эксплуатация результата​

  • Параметры запуска и рабочие настройки, пользовательский интерфейс, политика безопасности, интерпретатор, планировщик, резервные копии, мониторинг, логи, профайлер и чат. Своей статьи в brief нет: их запрашивают из ветки paradigm.

Мини-карта для ИИ​

  1. CLASS → тип объекта (множество объектов). Класс таблице не сопоставляется: в таблице лежат значения свойств, в ключевых полях — идентификаторы объектов, а классы параметров задают типы этих полей; свойство без явного TABLE попадает в таблицу, чьи классы ключей ему подходят.
  2. = DATA или = выражение → свойство.
  3. { ... } без = → действие (императивно).
  4. FORM → определение UI/запроса/отчёта.
  5. SHOW / DIALOG / PRINT → открыть/печатать форму.
  6. EXPORT / IMPORT → внешние форматы для свойств/форм.
  7. GROUP / PARTITION → агрегаты значений.
  8. GROUP AGGR / AGGR → агрегируемые объекты.
  9. NEWSESSION / APPLY / canceled() → управление транзакцией/сессией.
  10. EXTEND / ABSTRACT / += / +{ → точки расширения и полиморфизма.
  11. WHEN, <- WHEN → события на изменение данных; ON внутри FORM → событие формы: точка жизни формы, действие пользователя либо ON SCHEDULE по таймеру.
  12. Utils / Time / System / Authentication → стандартная библиотека (системные модули); там живут строковые, числовые функции и функции дат, currentUser, currentDate.
